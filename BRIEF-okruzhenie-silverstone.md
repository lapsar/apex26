# APEX '26 — бриф: детализация окружения трассы (Сильверстоун)

Задание для отдельного чата. Цель — подготовить **данные разметки окружения** трассы Сильверстоун:
крупные объекты (трибуны, здания) и зоны вылета (гравий / асфальт / трава / стена).
Готовый результат приносится в основной чат, там он встраивается в игру и проходит все проверки.

**Эту работу ведём по пути OSM + ручная доводка. Ширину полотна трассы НЕ трогаем — это отдельный, более поздний этап (влияет на физику).**

---

## 0. Что НЕ входит в эту задачу (важно)

- **Ширина трассы** (`track.HW`) — не менять. На неё завязаны вылет за трассу, расстановка соперников и всё окружение. Это отдельный этап позже, с полной регрессией.
- **Контур трассы, линия старта/финиша** — не трогать, они уже выверены.
- **Физика** — вылет на траву/гравий, контакт со стеной, овалы контакта с соперниками — не трогать.
- Уровень детализации: **узнаваемо, но стилизованно (low-poly), как сейчас.** Не фотореализм.

## 1. Контекст

**APEX '26** — браузерная гонка F1, один самодостаточный HTML, three.js **r128** инлайн, офлайн.
**Главное устройство — iPad mini 5.** Узкое место — число вызовов отрисовки (draw calls), не полигоны.
Русский интерфейс. Никаких внешних файлов и реальных логотипов (FIA, спонсоры, названия команд).

Сейчас окружение генерируется процедурно из контура: повороты ищутся по кривизне, вдоль них
раскладываются типовые объекты по правилам. Силуэт полотна точный (реальный контур), а всё вокруг —
правдоподобная, но **выдуманная** декорация: трибуны «через равные интервалы», гравий на каждом остром
повороте, стена сплошной лентой на одном отступе. Задача — заменить это на **реальные расположения и
размеры** для Сильверстоуна.

## 2. Как устроены данные трассы (система координат)

Трасса — замкнутый массив из `M` точек (`track.M`, у Сильверстоуна ~1470). Для каждого индекса `i`:

- `track.P[i]` — точка центра полотна: `THREE.Vector3(x, y, z)`, **y = 0 — уровень асфальта**.
- `track.F[i]` — единичный вектор «вперёд» вдоль трассы.
- `track.R[i]` — единичный вектор «вправо» поперёк трассы (перпендикуляр).
- `track.HW[i]` — полу-ширина полотна в этой точке (в метрах). Полная ширина = `2*HW[i]`.
- `track.S[i]` — накопленная длина от старта до точки i (метры).
- `track.K[i]` — кривизна (знаковая): изменение курса на ~24 м. `>0` и `<0` — разные стороны поворота.
- `track.length` — длина круга (Сильверстоун ~5891 м).

**Как поставить объект на местности:** взять ближайший индекс `i`, затем
`pos = track.P[i] + track.R[i] * off`, где `off` — смещение вбок в метрах (отрицательное — влево,
положительное — вправо). Ориентировать объект можно через `lookAt(track.P[i])` или по `track.F[i]`.

**Соответствие реальным координатам.** Контур получен из geojson `gb-1948` (bacinger/f1-circuits):
долгота→x, широта→z. Наш `track.P[0]` (до сдвига старта) = geojson[0] = `[-1.015349, 52.07879]`.
Линия старт/финиша сдвинута параметром `sfShift: 3120` (метров вперёд по трассе от начала контура) —
то есть индекс 0 в игре соответствует точке в ~3120 м по контуру. **Это критично:** чтобы OSM-объект
(в реальных lat/lon) лёг на правильное место, его надо перевести в ту же (x,z), что и контур, и найти
ближайшую точку `track.P` — а НЕ привязывать к «индексу 0», потому что старт сдвинут.

Реальные ориентиры Сильверстоуна для сверки (широта): север круга ~52.079, юг ~52.064.
Прямая старт/финиша (Hamilton Straight, где стоит Wing и главные трибуны) — в южной части, ~52.069.
Первый поворот Abbey — правый, сразу за линией старта.

## 3. Контракт `buildWorld` (это встраивается в игру — соблюдать)

Окружение строит функция `buildWorld()` один раз при старте заезда. Она уже вызывает:
`buildWidth()` → дорога/линии → `paintGrid()` → поребрики → гравий → стены (`wallRibbon`) →
шины (`tyreStacks`) → `buildScenery()` → `buildGantry()`.

**Доступные вспомогательные функции (использовать их, не переписывать):**

- `ribbonBetween(offA, offB, yLift, mat, vrep)` — сплошная лента вдоль всей трассы между двумя боковыми
  смещениями (функции индекса `i → метры`). Для дороги, линий, зон.
- `cornerRibbon(offInner, offOuter, yLift, mat, test)` — лента только на сегментах, где `test(i)` истинно.
  Для гравия/поребриков на нужных участках.
- `wallRibbon(sign, W, V, height, mat)` — стена вдоль трассы.
- `clearOfTrack(x, z, minDist)` → bool — точка дальше `minDist` от ЛЮБОЙ части полотна (чтобы объект не
  залез на трассу). **Обязательно проверять для каждого объекта.**
- `farFromOtherLegs(x, z, minDist, idx, win)` → bool — точка далеко от других «петель» трассы (не считая
  окно `win` вокруг своего индекса). Тоже проверять, чтобы объект не встал на соседний участок трассы.
- `seeded(seed)` → генератор псевдослучайных [0,1) (для мелкого разброса, если нужен).
- `cvtex(w, h, draw, rx, ry)` → THREE.Texture — процедурная текстура на canvas (все текстуры так сделаны:
  `grassTex`, `asphaltTex`, `gravelTex`, `kerbTex`, `armcoTex`, `crowdTex`). Логотипы не рисовать.

**Материалы:** только `MeshLambertMaterial` / `MeshBasicMaterial` (дёшево, как сейчас). НЕ `MeshStandard`
для окружения — дорого. Тени от окружения НЕ включать.

**r128-ограничения:** нет `CapsuleGeometry`, нет `BufferGeometryUtils`/`mergeBufferGeometries`
(в основном чате есть своя функция склейки — см. раздел 6), нет `OrbitControls`.

## 4. Формат результата (ГЛАВНОЕ — в этом виде вернуть)

Не переписывать `buildWorld` целиком. Вернуть **данные разметки** + при необходимости небольшие
функции-строители под новые типы объектов. Предлагаемая структура — объект разметки на трассу:

```js
const SCENERY_SILVERSTONE = {
  // зоны вылета: участки по накопленной длине S (в метрах от линии старта), сторона, тип, ширина зоны
  runoff: [
    // {fromS, toS, side:'L'|'R'|'both', type:'gravel'|'asphalt'|'grass', width: метры},
    {fromS: 250, toS: 520, side:'R', type:'gravel', width: 30},
    // ...
  ],
  // где стена идёт вплотную, где далеко (отступ от края полотна, метры)
  walls: [
    // {fromS, toS, side:'L'|'R'|'both', off: метры_от_края},
  ],
  // крупные объекты: трибуны, здания, пит-билдинг
  objects: [
    // {kind:'grandstand'|'building'|'pit', atS: метры, side:'L'|'R', off: метры_от_центра,
    //  w, h, d: размеры_в_метрах, rotDeg?: доворот, name?: 'для_сверки'},
  ],
};
```

Точные имена полей можно уточнить — важно, чтобы каждая запись **привязывалась к `S` (метрам вдоль
трассы) или к lat/lon**, а не к «индексу», и несла реальные размеры в метрах. Основной чат превратит это
в вызовы `cornerRibbon`/`ribbonBetween`/меши и вставит в `buildWorld`.

Если OSM-объекты берутся в lat/lon — можно вернуть их прямо в lat/lon + размеры; пересчёт в `S`/индекс
сделаю в основном чате (там уже есть привязка контура).

## 5. Источник данных OSM — известное ограничение

**В основном чате сеть ограничена белым списком (GitHub/npm/pypi), Overpass API и openstreetmap.org
оттуда НЕ доступны (проверено: HTTP 403, «host not in allowlist»).** Поэтому:

- В отдельном чате сначала попробовать вытянуть данные из OSM (Overpass): трибуны `leisure=grandstand`,
  здания `building=grandstand`/`building=*` в паддоке, при наличии — барьеры. Область Сильверстоуна
  примерно `bbox 52.062,-1.026,52.080,-1.007`.
- **Если сеть и там ограничена** — размечаем вручную по спутниковому снимку/официальной схеме: это
  выбранный запасной путь. OSM даёт «скелет» (места и размеры), рука дорабатывает гравий/асфальт/стены,
  которых в OSM обычно нет.
- Гравийные/асфальтовые зоны вылета в OSM почти не размечены — их в любом случае размечаем вручную по
  снимку (видно по цвету: бежевый гравий, серый асфальт).

## 6. Производительность (под iPad mini 5) — жёстко

- Узкое место — **draw calls**, а не полигоны. Ориентир: окружение НЕ должно добавлять много отдельных
  мешей. Сейчас трибуна = 2 меша, дерево = 2, шина-стопка = 1.
- **Обязательна склейка (merge).** Всё статичное окружение строится один раз и не меняется — идеальный
  кандидат. В основном чате есть готовая функция склейки геометрий по материалу (написана для болида,
  склеивает N мешей одного материала в 1). Поэтому: **однотипные объекты делать одним материалом**
  (все трибуны — общий материал «толпа», все здания — общий, весь гравий — один и тот же материал), тогда
  склейка даёт максимум выигрыша. Разнобой материалов убивает merge.
- Ленты (`ribbonBetween`/`cornerRibbon`) уже дёшевы (один меш на ленту) — предпочитать их для зон.
- Не включать: тени от окружения, прозрачные сетчатые заборы, отдельных зрителей, отражения.
- Дальние объекты можно упрощать/не строить (небо «едет» за камерой на 1700 м — дальше не видно).

## 7. Визуальная сверка (как проверять в отдельном чате)

Финальная сверка «как в игре» — всё равно в основном чате и на устройстве (там настоящий движок,
камера кокпита, свет). В отдельном чате проверяем **соответствие реальности**:

1. **Карта вида сверху с наложением.** Рисовать контур трассы + размеченные объекты (трибуны —
   прямоугольники, зоны — цветом, стены — линиями) и класть рядом со спутниковым снимком/схемой F1.
   Так пользователь сверит «трибуна на месте и того же размера». (Так сверяли линию старта — работает.)
2. **Опционально — 3D-крутилка** облегчённой сцены с трассой и декорациями (как крутилка болида), чтобы
   облететь камерой и оценить объём/масштаб.
